## TDR-027: Compact Ingredient List with AddIngredientModal
**Date**: 2026-09-06
**Status**: Accepted
**Context**: `IngredientForm.tsx` (food) and `WaterIngredientsForm.tsx` (water) rendered every ingredient as a fully-expanded card at once — name/search field, amount+unit row, calories field, macro pills, and (for food) a barcode scan icon, all repeated per row. With 3+ ingredients this became a long vertical scroll of near-identical form clusters, hard to scan and poorly suited to a phone screen. See [issue #10](https://github.com/jamundie/FoodTrackerApp/issues/10).
**Decision**: Replace the always-expanded card list with a compact row list — one row per ingredient showing name and amount+unit, with Edit/Trash icon actions reusing the existing `entryActionButton`/`editButton`/`deleteButton` styles from `FoodEntriesList`/`WaterEntriesList`. A new shared `components/AddIngredientModal.tsx` holds the actual single-ingredient form (previously inline in each card) and is used by both `IngredientForm` (`mode="food"`, wiring `FoodSearchInput` + `BarcodeScannerModal`) and `WaterIngredientsForm` (`mode="water"`, plain fields only). The modal owns a local draft copy of the ingredient — nothing touches the parent's `ingredients` array until Save. Add flow: Save commits the draft then shows "Add Another" / "Done" so several ingredients can be added back-to-back without reopening the modal. Edit flow (`initialData` prop present): a single Save commits and closes immediately, no add-another prompt. Delete shows an `Alert.alert` confirmation, matching the existing whole-entry delete pattern from TDR-020.

This required two supporting hook changes in `useFoodEntryForm.ts` / `useWaterEntryForm.ts`: `ingredients` now seeds as `[]` for new entries (previously a single blank row), so the compact list starts empty with just the "+ Add Ingredient" button; and `removeIngredient`'s guard preventing removal of the last row was relaxed to allow the list to reach zero — `validateForm` already requires at least one valid ingredient at submit time, so this is safe. `addIngredient`/`updateIngredient`/`applyNutritionToIngredient`/`removeIngredient` signatures are unchanged; the modal drives them exactly as the old inline card did, just via a `commitIngredientData` helper that writes each defined field of the modal's draft back through `onUpdateIngredient` after calling `onAddIngredient` (for new rows) or directly (for edits).
**Consequences**: Both ingredient sections now scale to many ingredients without an ever-growing scroll. The Gemini Vision photo-analysis fan-out (`analysePhoto` in `useFoodEntryForm.ts`) is unaffected — it already handled an arbitrary-length `ingredients` array via push/replace-in-place logic, which degrades gracefully to "always append" when the array starts empty. Existing form validation, edit-entry pre-fill, and barcode/OFF lookup behavior are all preserved, just presented through the modal instead of inline. `IngredientForm.test.tsx` and `WaterIngredientsForm.test.tsx` were fully rewritten around the new interaction model; a new `AddIngredientModal.test.tsx` was added under `components/__tests__/modals/`.
