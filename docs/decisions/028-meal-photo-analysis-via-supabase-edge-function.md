## TDR-028: Meal Photo Analysis via Supabase Edge Function
**Date**: 2026-10-05
**Status**: Accepted
**Context**: TDR-021 called Gemini Vision directly from the device using `EXPO_PUBLIC_GEMINI_API_KEY`. `EXPO_PUBLIC_*` values are inlined into the JS bundle at build time, so a standalone Android build made without the key in `.env.local` (or an EAS build, where the gitignored `.env.local` is absent) failed with "Gemini API key is not configured", and any build that did include it exposed the key to anyone who unpacked the APK. TDR-026 already closed this gap for report generation.
**Decision**: Moved the Gemini Vision call into a second Edge Function, `analyse-meal-photo`, which reads the existing server-side `GEMINI_API_KEY` secret. `lib/geminiService.ts` keeps its public `analyseMealPhoto(photoUri): FoodSearchResult[]` contract (so `useFoodEntryForm` is unchanged): it base64-encodes the photo on-device and calls `analyseMealPhotoRemote` in `trackingService.ts`, which invokes the function. The function authenticates with `withSupabase({ auth: 'user' })`, validates MIME type and size, and returns `{ ingredients }`. Failed invocations now surface the function's own `{ error }` body via a shared `extractFunctionErrorMessage` helper rather than supabase-js's generic "non-2xx" message.
**Consequences**: `EXPO_PUBLIC_GEMINI_API_KEY` is no longer read by the app and can be removed from `.env.local`/`.env.example`. The photo is sent to the function as base64 in the request body (bounded by a ~10 MB size cap). Photo analysis now requires a signed-in user and network access to Supabase. No per-user rate limit is applied yet (unlike reports); this is the natural follow-up. The client change requires a new APK build to ship.
